3. 机器人开机自动启动 Apex 后端及 host-control、底盘录制桥、带门控的手柄服务。相机、Robot Control、Teleop + Replay 当前均不是开机自启。本轮实际状态也均为 inactive。

5. 按既有身体遥操流程完成连接、必要标定和控制使能，确认身体/头部、EEF、IK、底盘、相机持续有数据。启动服务、使能控制、开始Record是三个不同步骤；Record不代替机器人准备操作。
6. 在 av-pipeline 单独启动手部：


这个命令会连接并使能真实MANUS/Sharpa，开始跟随；无 `--execute` 时仅打印计划。它先启动记录桥、MANUS和映射，等待双手目标稳定后连接Sharpa。当前 Apex 的 Tool 类型仍为 dm，不能将 Tool 启动按钮当作该 Sharpa 模块入口。

9. 点击原 **Stop**，等待结束响应。协调器等待原生停止、队列排空、相机结束和落盘审计，再写completion。以 `capture_completion.json` 的 COMPLETE及哈希校验为准。
10. 如需继续下一条，身体和手部遥操可保持运行；如结束作业，先停止录制，再退出手部终端及按现有流程停止身体遥操/控制。Stop录制本身不会解除手部使能。

目前只验证过隔离模拟数据；没有实际身体、双手与相机一起生成的已验收新格式正式episode。

## 三、Raw不是76维数组

Raw保存原频率、多topic、多种ROS消息。76维是训练导出时才组织的向量。

```text
/home/user/gento_replay_bags/<录制名>/
├── <录制名>_0.mcap           身体、双手、IK、底盘、context、capture_event等
├── metadata.yaml
├── video/.../*.mcap         相机原始编码流及自己的metadata
├── capture_time.json
├── capture_manifest.json
└── capture_completion.json
```

- 数值时间轴：机器人MCAP log时间，robot_receive，int64纳秒。
- 手部真实反馈：`/hand_left/joint_states`、`/hand_right/joint_states`。
- 手部action来源：`/hand_left/joint_commands`、`/hand_right/joint_commands`，表示SDK成功提交的目标，不是手套请求，也不是关节实际到位。
- `/recording/sharpa/context` 保留session/seq、序列号、源时间及SDK结果，与JointState逐条关联；不能只拷贝四个手部topic而丢掉context。
- receiver时间与MCAP时间不同，原源时间另保留；统一接收时钟不等于硬件同时采样。
- 相机Raw按 `format` 解码；历史实测为H.264四宫格，不可将每个CompressedImage包当作JPEG。
- 原始episode完整拷贝后，导入器另包装为 `data/raw_data/apex_data/<task>/episode_XXXXXXXX/payload/`；传输manifest与capture manifest含义不同。

## 四、已找到脚本及匹配结论

下列源码位于 av-pipeline；路径以 `/home/descfly/apex_n_sharpa` 为公共项目根，手部目录以其 `integrations/manus_sharpa` 为入口。

| 环节 | 入口 / 实现 | 匹配结论 |
|---|---|---|
| Raw导入 | `read_raw_data` / `src/read_raw_data/main.py` | 能保留完整目录与新sidecar；读capture_time识别新目录时间；但不检查capture completion是否COMPLETE，也不拒绝diagnostic |

## 五、实读数据与具体断点

实读旧任务 `robot_import_20261024_egoav_v4` 的 episode_00000002：

- LeRobot：314帧、20Hz，主state/action/validity均为[314,78]。
- 主向量身体27:32全零且validity为0；双手44维也全零且validity为0。
- 辅助列 `observation.body_joints` 为[314,5]且有实际数值；`action.body_controller` 为[314,3]，`action.head_controller` 为[314,2]，也有实际数值。
- 身体HDF5包含1755条5关节反馈、1755条19关节反馈、3928条身体目标、3929条头部目标、874条底盘命令及8781条19维IK seed。
- 身体HDF5当前capture_id为空；新认证诊断Raw有capture_id，但没有旧转换器所读取的episode_metadata.json。
- 新手部HDF5有4条流，每流90条×22维，capture_id与诊断Raw一致；这证明手部提取接口可用，不代表真实硬件已通过验收。

明确不匹配点：

1. **认证门槛不统一。** 公共导入/身体转换未接capture_completion门槛，文件复制稳定或HDF5 complete不等于录制认证完成。
2. **capture_id来源不统一。** 身体转换读episode_metadata.json；新录制写capture_manifest/capture_time。新的身份未自动进入身体HDF5。
3. **双手输入接口不统一。** 新链路输出hands.hdf5；公共LeRobot转换器只找外置盘 `data/raw_data/sharpa_data/<task>/episode_XXXXXXXX/payload/sharpa.json`，要求JSON streams结构。不会自动读取新手部HDF5。
4. **目录约束不统一。** 公共转换器数据限制在外置盘的 `apex_n_sharpa/data`；手部输出位于 `apex_n_sharpa/manus_sharpa/data`。直接把文件路径塞给旧接口也不能完成适配。
5. **维数、槽位与mask未升级。** 仍按78维处理；新76维需真实身体填27:32、删除夹爪54/77、右手改54:76，并同步全部schema/mask/statistics/metadata。
6. **公共时间网格未统一出口。** 身体与手部已同为robot_receive，但必须合并必需流确定公共网格和capture_id，不能仅按episode编号拼接。

只读函数探测确认：传入76维profile，现有build立即返回“未知输出profile”；认证提取器默认拒绝诊断Raw。没有运行会创建或覆盖输出的完整转换作业。

## 六、建议修改范围（本轮未实施）

保留现有身体转换和新录制Raw格式，统一认证校验及capture_id读取；将四条手部流和context解析接到统一HDF5或其有明确契约的手部sidecar；新增76维profile，正确填写身体五维与双手44维，重算mask/统计并保留原频率IK/底盘/手部replay来源。用同一认证Raw做全字段往返及错误输入拒绝测试。

不需要从头重写已有身体/相机转换；需要补的是新的统一数据契约与现有脚本之间的接口。
